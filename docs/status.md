# 现状与边界 / Where this stands, and what is missing

这份文档回答三个问题：

1. 哪些东西**真的跑通了**——在我自己的 M10 上，用我自己的输入验证过。
2. 哪些东西**只在我的机器上成立**——因为依赖我的标定、我的原厂文件、我的机号。
3. 要让它在**任何一台 M10** 上成立，还缺什么。

第三项是这份仓库存在的理由。

---

## 0. 先说清楚边界

**这个仓库不提供固件写入器。** 没有刷机路径，没有设备协议发送器，没有可以生成的
`.FW`。原因不是技术做不到，而是这件事必须先在公开场合把方案讨论清楚，再由每个人
对自己的机身负责。

仓库里有的东西都是同一类：**对你自己已经拥有的文件做分析、校验和离线重算**。
你可以用它读懂一个包、验证一个假设、算出裁切参数。它不会碰你的相机。

---

## 1. 已经跑通的部分

以下每一项都在实机上跑通过——**在作者的机器上**。这就是它们值得继续的理由，也是它们
现在还不算"公共方案"的原因。

### 1.1 XPan 画幅（65:24）

裁切参数完全解出，包括几何换算和配置写入位置。

- 三轴偏移公式：宽 `+896×c0c`、高与原点 `+448×c0e`
- 目标比例写入 `cfg[+0x12]`，输出尺寸从 `cfg[+0x14]`

**跑通到什么程度**：参数推导完整，补丁已应用到自备镜像并打包成结构完整的
固件（容器校验 45 项全过），但**从未刷入真机**。

**必须说清楚的一件事**：上面这些常数（`2224` / `2208` / `6016` / `896` /
`0xc0c` / `0xc0e`）**在本仓库的任何代码文件里都不存在**，只出现在文档中。
`modules/framing/` 是实时取景框线几何（3600×2400 逻辑面），与 XPan 裁切不是
同一回事。所以读者目前无法在代码层复算这条结论——这正是
`docs/contributing-ideas.md` 里 B1 那条任务要解决的问题。

**为什么还不是公共方案**：比例基线有两个候选值（2224 / 2208），静态无法判定，
只在一台机器上确认过其中一个。需要第二台、第三台机器给出各自的正确基线。

**两个未解决的风险**：补丁落点 `0x421f6ee0` 在文件里是 981 字节全零填充，
但运行时是否被当作缓冲/BSS 无法静态排除；`cfg+0x18..+0x24` 四个标量的语义
未解，若它们参与裁切矩形，补丁会自相矛盾。

**需要一台 M10 和一次实测**——但注意真机刷写有风险，见 §4。

### 1.2 ASC 滤镜（10 Classic / 01 Contemporary）

双 Y 通道混合方案，含真实的资源解析器和有序 C 应用步骤。

- `modules/asc/`：354 行，含 b2y 处理与选择器集成
- 8 个 native 窗口 + 强制的 105 项 B2Y 混合

**跑通到什么程度**：混合逻辑完整，10 个 Classic 风格和 1 个 Contemporary 风格
的配方都能求出结果。

**为什么还不是公共方案**：需要一份合法的原厂 ASC 资源才能算出真实像素。仓库**不
分发**这份资源，你需要自己从你合法拥有的相机或软件里取。

**缺口很具体**：原生 acquire/idle/cache/hardware 的调用边界没有闭合。

### 1.3 胶片滤镜（800T + 18 个 GRKit 配方）

通用引擎，不是硬编码的查表。

- `modules/film/`：31 个文件，2165 行
- 支持可选的 post/hue、单色、曲线节点、选择性调色
- 14 个彩色 + 4 个单色配方

**跑通到什么程度**：主机端参考实现完整，全部 19 款胶片都能求值。

**为什么还不是公共方案**：只在主机端参考域里成立。M10 的实际色彩域、bank codec、
原生选择器都还没在实机上闭环。

**缺口**：需要一次真实的实机色彩域对照。

### 1.4 触摸

- `modules/touch/`：457 行
- M10-P 的 `calculate_gesture` 是 3336 字节，M10 是 3264 字节，前 15 条指令
  逐字节相同；M10-P 另有一段 106 字节的白名单分派（`0xCE5D8`–`0xCE646`）

**跑通到什么程度**：`modules/touch/` 实现的是**事件路由与池生命周期管理**——
生产者尾部修复（`tr_forward` / `tr_completed_tail`）、载荷事件过滤
（`0x113`–`0x116`、`0x120`–`0x124`、哨兵 `0x211`）、调试态谓词
（`0x13a` / `0x13d`），以及 `trc_pool_init/begin/finish/copy/reclaim_metadata`。

**这里更正一处此前的错误描述**：早期版本说该目录含"手势累加器状态机、状态 0–3
的完整转移"。**本仓库里没有这样的状态机**——`grep -ri gesture modules/touch/`
只有一条命中，是注释 `/* full raw status; no gesture wrapper */`。手势字节数
（3336 / 3264）来自私有分析，不在本仓库中可复算。

**为什么还不是公共方案**：缺少生产者调用点、7 参数 ABI、池的生命周期和同步。

**缺口**：这是一项真正的研究任务，不是改个常量。好消息是路径已经画出来了。

## 2. 为什么这些"只在我机器上成立"

诚实地说清楚这一点，比假装它们是通用方案更有用。

| 依赖 | 影响 |
|---|---|
| 我的机身标定 | 标定类数据换机器就必须重算 |
| 我的原厂资源 | ASC 资源不分发，你必须有自己的一份 |
| 我的固件版本 | 偏移是 3.22.23.38 的；其他版本要重新核对 |
| 我的实测基线 | 比例、色彩域这类参数一台机器给不出定论 |

这不是能力不足，是这类工作的固有性质。**任何声称"一个方案通吃所有机器"的说法都
可疑**，包括我的。

## 3. 让它变成公共方案需要什么

以下每一项都可以独立认领。

### 3.1 需要第二台、第三台机器

- **XPan 比例基线**：你的机器上 2224 还是 2208 正确？
- **色彩域对照**：把同一张 RAW 过一遍主机参考实现和实机，色差在哪

做这些不需要改任何东西，只需要**测**和**报**。

### 3.2 需要一份干净的实测记录

- 一次完整的固件更新流程记录（哪些块被写、什么顺序、失败时怎么表现）
- 主引导阶段的转储，用来确认恢复路径到底存不存在

这类记录价值极高，因为它能回答"做错了会怎样"——而这是所有方案的前提。

### 3.3 需要有人把解析推进到写入

触摸、取景框、低噪快门都停在"解析清楚了，但没接上写入路径"。

这不是危险的部分，是**最需要人手**的部分。如果你愿意做，从 `modules/touch/`
的状态机开始最好——它的路径最完整。

### 3.4 需要固件版本覆盖

目前的偏移全部针对 **3.22.23.38**。4.x 系列没有核对过。

有价值的工作：**把同一批符号定位方法应用到另一个版本**，看偏移是否稳定。
工具（`tools/m10sym/`）就在仓库里，方法在 `docs/symbol-table.md`。

---

## 4. 关于"为什么不直接开源全部"

作者的选择是：**先公开可以讨论的部分，把需要负责的部分留给讨论结果**。

具体地说——固件写入、身份改写、包构造这类能力，如果直接公开，会先被用来做不该做
的事，而不是被用来把方案做对。所以这部分留在私有树里，等公共讨论有了结论再说。

这不影响你想做的事：上面第 3 节列的每一项，**都不需要写入能力**就能推进。

---

## 5. 你可以怎么开始

```sh
# 1. 验证工具链本身是对的
python3 -m unittest discover -s tests

# 2. 读一份你自己的包（只读；需要你自备固件包）
python3 codec/independent_verify.py <your.fw>

# 3. 看符号提取器怎么工作
python3 tools/m10sym/extract.py --help
```

第 2 条需要你自己的一份固件包。完全不碰固件也能验证 codec：
`node --test codec/test_builder.mjs`（24 个合成用例）。

然后挑第 3 节里的一项。如果你想认领某一项，开个 issue 说明你的机型和固件版本，
我们就能知道这个方案到底能不能通吃到别的机器上。

**不需要硬件的具体任务**（带入口文件与验收标准）见
[docs/contributing-ideas.md](contributing-ideas.md)。

---

## 6. 一句话总结

**能做的部分做完了，通用的部分还没开始——因为那需要不止一台机器。**
